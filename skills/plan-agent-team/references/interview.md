# The interview — what each question is actually testing

Ask few. Infer much. The point of each question is in the second column; once
you have that, move on.

| Question | What it decides |
|---|---|
| What work repeats? | Whether a fleet is the right shape at all. No repetition, no fleet |
| Where does work come from? | Whether queues will fill. The most predictive single answer |
| What is the cost of being wrong? | How strict the gate is, and whether a human sits in the chain |
| What is checked today, and by whom? | Whether the first agent you build is a checker rather than a maker |
| What must a human still decide? | Where accountability is real, so the rest can carry none |
| What is already automated? | Hidden queue producers — usually generating records nobody owns |
| What tools can you not give an agent today? | Which roles are blocked, so you do not design a team you cannot staff |

## Follow-ups worth having ready

**If "work comes from me thinking of things"** — one producer will not sustain
five agents. Ask what would generate work without them: user reports, monitoring,
a recurring review, an audience. If nothing does, plan two agents and a habit,
not a fleet.

**If "nothing is checked today"** — do not treat this as an obstacle. It is the
strongest argument for the method, and it means the build order starts with the
checker. Say that explicitly; people expect to start with makers.

**If "everything touches everything"** in the repo — there are no lanes. Either
the codebase needs boundaries first, or the honest answer is one maker rather
than four fighting over the same files.

**If they name ten roles unprompted** — they are describing an org chart, not a
fleet. Ask which three, if staffed today, would change the outcome this month.
The rest go on the "later" list with triggers.

## Things not to ask

- **Do not ask what to call them.** Propose names. Naming is the fun part and
  people happily spend an hour there instead of on boundaries.
- **Do not ask how many agents they want.** The number is an output.
- **Do not ask about scheduling intervals** in the planning phase. That is a
  launch decision and it distracts from the roster.
- **Do not ask anything you can measure.** Commit history, tracker states,
  surfaces and staleness are all observable. Asking them costs credibility.
